## 01｜有 Git，为什么多人 AI 开发还是返工？

**备选标题**

1. 三个人都在用 Codex，为什么合并时还是返工？
2. Git 记得每次提交，却记不住我们怎么决定需求
3. AI 写代码很快，团队理解跑偏也很快

**封面字**

> 代码都能合并，需求却没对齐？
>
> 多人 AI 开发真正容易漏掉的一步

**正文（可直接发布）**

设想一个多人 Codex 协作场景：

三个人各自在自己的工作区开发，分支干净、提交也规范。合并前一对需求，才发现 A 做的是“先登录后选团队”，B 按“先选团队再登录”写了接口，C 的页面又基于第三种理解。代码都有版本，最初的决定却没有共同版本。

Git 很擅长回答“谁改了哪行代码”。多人 AI 开发还需要回答：每个人理解的目标是不是一致？有分歧谁来裁决？任务按哪个方案开工？中途改需求会影响谁？

我做的 Vibe-Git，就是给这些问题加一条协作流程：成员先提交各自的 Markdown 提案，队长对齐差异并确认分工；任务发布后由负责人主动开工；需求变化再走影响审核和确认。Git 仍然管理代码，Vibe-Git 记录团队此刻共同认可的意图和任务状态。

如果你也遇到过“大家都很忙，最后做的不是同一个产品”，可以到 GitHub 搜索 **TFboy1/vibe-git** 看看。它目前是 0.20 源码版本，适合愿意一起试用和反馈的小团队。

**配图页文字提纲**

1. 封面：代码都能合并，需求却没对齐？
2. 场景：A、B、C 三人各自用 Codex 开发，登录流程出现三种理解。
3. 问题：Git 记录提交；需求版本、裁决和开工依据仍需要团队管理。
4. 方法：个人提案 → 对齐分歧 → 发布任务 → 明确开工。
5. 收尾：Git 管代码，Vibe-Git 管多人 AI 开发中的共同意图。GitHub：TFboy1/vibe-git。

## 02｜让三个 Codex 按同一份方案开工

**备选标题**

1. 多人用 Codex 开发，我给“开工”加了一道确认
2. 从三份想法到一份分工：Vibe-Git 怎么用？
3. AI 开发团队的提案、裁决和任务发布流程

**封面字**

> 三个人三个想法
>
> 怎样变成一份可执行的分工？

**正文（可直接发布）**

多人用 Codex 做同一个项目，最怕把“大家都提过想法”当成“大家已经达成一致”。我希望开工前能留下三个清楚的东西：每个人的提案、分歧的处理结果、最终是谁负责哪一块。

Vibe-Git 的流程很直接：

① 队长在自己的 Git 工作区运行 `vibe-git host start`，把生成的加入命令发给队友。

② 每位成员在自己的工作区连接，并用 `vibe-git plan submit <文件.md>` 提交自己的方案。其他人可以查看，但不能替你改提案。

③ 队长运行 `vibe-git align start`，查看对齐稿和冲突选项。该裁决的先裁决，再指派并发布任务。

④ 负责人领取任务后，自己执行 `vibe-git task start <task-id>`。发布任务不等于让所有 Codex 自动抢跑。

网页可以看团队状态，实际操作仍以 CLI 为主。提案、对齐稿和任务状态集中在同一个房间，团队也能看见任务现在由谁推进。

这是我正在迭代的 0.20 源码版本。想试试的话，GitHub 搜索 **TFboy1/vibe-git**；README 有安装步骤和完整命令手册。需要 Node.js 24+、Git 和 Codex CLI。

**配图页文字提纲**

1. 封面：三个人三个想法，怎样变成一份分工？
2. 第一步：队长建房间，成员在各自 Git 工作区加入。
3. 第二步：每人提交自己的 Markdown 提案；保留来源与当前版本。
4. 第三步：对齐差异 → 裁决 → 指派 → 发布。
5. 第四步：负责人领取并明确开工；团队网页查看状态。
6. 收尾：源码与完整命令见 GitHub：TFboy1/vibe-git。

## 03｜开发中突然改需求，怎样知道会影响谁？

**备选标题**

1. AI 团队开发到一半改需求，先别让所有人停工
2. 需求变了，哪几个 Codex 任务真的受影响？
3. 我给多人 AI 开发做了一个需求变更审核流程

**封面字**

> 开发到一半改需求
>
> 先搞清楚影响范围

**正文（可直接发布）**

项目做到一半，突然要调整登录流程。最难的不是把新要求发到群里，而是判断：哪些任务正在依赖旧流程？谁需要补证据？哪些人可以继续做？

Vibe-Git 允许成员把变更写成 Markdown，用 `vibe-git pr submit <文件.md>` 提交。这里的 PR 是产品内部的**需求变更单**，不会创建 GitHub Pull Request。

审核会结合任务负责人在自己工作区提供的受限 Git 路径证据；影响说不清的任务需要继续补证。队长可以在开发中提前发起审核，查看逐份结论，再决定应用或退回。审核结果不会自己变成新需求；开发中的处理也会针对受影响任务进行。

我想要的是一个很朴素的结果：需求变了，团队先看到影响，再作决定。这样继续开发的人有依据，需要调整的人也知道为什么调整。

Vibe-Git 目前是 0.20 源码版本，跨设备真实房间还需要在使用环境联调。如果你愿意试用并反馈，GitHub 搜索 **TFboy1/vibe-git**，README 里有工作流和当前边界。

**配图页文字提纲**

1. 封面：开发到一半改需求，先搞清楚影响范围。
2. 场景：登录流程调整，多个任务正在并行开发。
3. 提交：成员上传 Markdown 需求变更单；它不是 GitHub PR。
4. 审核：收集受限路径证据，缺证据的任务先补证。
5. 决定：队长查看影响结论，应用或退回；处理真正受影响的任务。
6. 收尾：GitHub 搜索 TFboy1/vibe-git，查看 README 与使用手册。
