02 / CHOOSE YOUR ROLE

第一次安装后，先回答一个问题。

你是要创建房间的队长，还是要加入别人房间的队员？不要两套命令混着执行。

01CAPTAIN / 队长

你来开房间、定方案、发任务。

适合项目负责人或负责协调的人。队长不是“代码写得最多的人”，而是负责把大家的提案对齐并发布可执行任务的人。

CAPTAIN WORKSPACE
cd C:\path\to\your-project
vibe-git host start
vibe-git open
  1. 把成功回执中的加入命令私下发给队员。
  2. 等至少一份提案上传，再开始对齐。
  3. 裁决冲突后发布任务，不要让大家各自猜。

可以这样对 Codex 说：
“我是队长，帮我检查当前工作区，启动 Vibe-Git 房间，并告诉我哪一行是给队员的加入命令。”

02MEMBER / 队员

你来加入房间、提方案、做任务。

适合在自己的电脑上开发的人。每个队员都有自己的 Git 工作区，只能更新自己的提案，不会覆盖别人的方案。

MEMBER WORKSPACE
cd C:\path\to\your-project
vibe-git connect "<队长给你的完整 URL>"
vibe-git status
vibe-git open
  1. 先确认你在要写代码的项目目录。
  2. 把队长给你的完整 URL 放进 connect。
  3. 让 Skill 帮你起草提案，确认后再上传。

可以这样对 Codex 说：
“我是队员。这是队长的加入命令，请帮我连接房间，再阅读项目起草提案，确认后上传。”

不知道自己是哪种？ 能创建房间并把加入命令发给别人，就是队长；拿到别人发来的加入命令，就是队员。两者都要在自己的项目 Git 工作区执行，不要在空目录或 Vibe-Git 源码目录里操作。

04 / SKILL DOES THE BORING PART

你说人话，Skill 帮你变成命令。

你不需要背命令。先说你想完成什么，Skill 会判断角色、整理 Markdown、提醒风险，再在你确认后上传。

01 / 提案

自动整理并上传 plan

提案不是一句“我想做登录”。它至少应该说明目标、当前问题、实现方案、验收标准和风险。

“我是队员。请阅读当前项目，整理一份提案，先展示给我确认，确认后保存成 UTF-8 Markdown 并执行 vibe-git plan submit。”

提交相同内容会幂等；修改内容会生成新版本。你不能用队长身份替别人修改提案。

02 / 需求变更

自动整理并提交内部 PR

这里的 PR 是 Vibe-Git 内部需求变更单，不是 GitHub Pull Request。它用来记录“改什么”和“会影响谁”。

“我要把登录流程改成先选团队。请分析当前任务影响，生成变更单，提醒我这是内部 PR；确认后执行 vibe-git pr submit。”

Skill 会把原需求、修改内容、影响任务、兼容性和验收标准整理清楚，不会擅自应用变更。

03 / Codex 池

自动连接专用审核 Codex

如果你要检查需求改动影响哪些代码，先为当前节点绑定专用审核账号。它不替换你的日常 Codex。

TERMINAL
vibe-git codex bind
vibe-git codex status

出现 device-auth 页面时由你完成授权。不要把凭据、加入密钥或本地配置发给任何人。

04 / 任务

从领取到确认完成

发布任务不等于自动开工。负责人要自己拉取任务、确认步骤、明确开始，Codex 结束后还要同步并确认。

MEMBER
vibe-git task list
vibe-git task pull <task-id>
vibe-git task start <task-id>
vibe-git task sync <task-id>
vibe-git task done <task-id>

需要补充实现步骤时先用 task push；需要把本地改动接入任务时再按实际状态使用 task integrate。

05 / 审核

需求改了，先查影响再决定

队员提交内部变更单后，队长可以在开发中提前发起审核。审核结果是建议，不会自动改代码或自动应用需求。

CAPTAIN
vibe-git review start --force
vibe-git review status
vibe-git review apply <review-id>
# 或者
vibe-git review reject <review-id>

如果状态是 NEEDS_EVIDENCE，先让受影响节点补证，不要强行 apply。

06 / 高级能力

阶段、契约和工作流

普通项目可以先不用这些命令。大型协作需要分阶段推进时，队长管理 stage，团队用 contract 记录确认点，成员查看 workstream。

ADVANCED
vibe-git stage activate <alignment-id>
vibe-git contract list
vibe-git contract ack <contract-id>
vibe-git work list
vibe-git work pull <workstream-id>

不确定是否需要高级能力时，先让 Skill 读取 status 和面板状态，不要凭空创建阶段或契约。

06 / A COMPLETE EXAMPLE

一个完整项目到底怎么走？

下面是一条从第一次安装到需求变更的真实顺序。你可以把它复制给队友。

  1. 01

    安装

    所有人安装 Skill、CLI，并运行 vibe-git --help。

  2. 02

    队长开房

    队长在自己的项目工作区运行 host start，把加入命令私下发给队员。

  3. 03

    队员入房并提案

    队员运行 connect，让 Skill 阅读项目，确认后执行 plan submit。

  4. 04

    队长对齐并发布

    队长执行 align start，解决冲突，再执行 tasks publish。

  5. 05

    负责人开发

    负责人执行 task pull 和 task start；Codex 结束后同步并确认 task done。

  6. 06

    需求变更

    有人提出新需求，Skill 整理 Markdown；确认后 pr submit，队长审核影响并决定应用或退回。

07 / TROUBLESHOOTING

卡住了，先看这几条。

遇到异常时不要重复乱试。先看状态，再看日志，把错误原文交给 Skill。

我不知道自己该用队长还是队员命令。

你要创建房间并邀请别人，就是队长；你拿到别人发来的加入 URL，就是队员。队长用 host start，队员用 connect，不要反过来。

Skill 安装了，但命令不存在。

Skill 和 CLI 是两件事。先确认 vibe-git --help 是否可用；不可用就按 CLI 安装步骤执行 npm.cmd ci、npm.cmd run build、npm.cmd link，再重新打开终端。

队员连不上房间。

确认队员在自己的项目 Git 工作区，确认复制的是队长回执中的完整加入命令，确认 Host 仍在运行。队长可运行 vibe-git host status，队员可运行 vibe-git logs。

为什么 Codex 结束了，任务还没完成？

Codex 退出不等于 Vibe-Git 收到完成确认。队员需要先执行 task sync，确认状态新鲜，再由自己执行 task done。

“PR”为什么没有出现在 GitHub？

pr submit 是 Vibe-Git 内部需求变更单，用来审核任务影响，不会创建 GitHub Pull Request。真正的代码提交仍然使用 Git。

需要把哪些东西发给别人？

只把队长生成的加入命令发给预期队员；不要分享日常 Codex 凭据、client.json、审核账号目录或公开加入密钥。

仍然不会？ 在当前项目工作区运行 vibe-git status 和 vibe-git logs，把输出中的错误原文交给 Codex，并说明你是队长还是队员。不要只说“不能用”，否则 Skill 无法判断是安装、网络、身份还是工作区问题。
