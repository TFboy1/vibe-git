# 需求变更与重新派发

工作台的 **Issues** 负责需求变化。CLI `pr submit` 使用内部需求变更记录，不会创建 GitHub Pull Request；代码合并另走 [Pull requests](./git.md)。

## 步骤 1：提交需求变更

> **操作人**：队长或成员。**前置条件**：首轮正式需求已派发。**入口**：Issues → **“New issue”**。

1. 填写变更标题，在 Markdown 正文写清原需求、修改内容、原因、影响任务和新的验收。
2. 检查页面“基于 R…”是否是实际阅读的正式需求版本。
3. 内容确认后点击 **“提交需求变更 Issue”**。
4. 在列表确认记录进入待审核状态。

CLI 可提交 UTF-8 Markdown，例如：

````markdown
# 增加按完成状态筛选

## 原需求
R1 仅展示全部待办。

## 修改内容与原因
增加“全部、未完成、已完成”筛选，方便查看当前工作。

## 影响与兼容
涉及 Vue 列表和接口筛选参数。未提供筛选参数时保持原行为。
真实受影响任务由队长联合审核确认。

## 新验收
- 三种筛选返回符合条件的结果。
- 空结果显示明确提示。
````

```powershell
vibe-git pr submit .\change-filter.md
vibe-git pr list
```

**成功结果**：出现已提交记录和真实 ID。**失败处理**：正式需求已更新时先核对新版本，再点击页面“已核对，改为基于新版提交”；没有首轮正式需求时先完成派发。**下一步**：队长选择审核批次。

## 步骤 2：选择一批 Issue 统一审核

> **操作人**：队长。**前置条件**：有待审记录，同阶段无另一个活动审核。**入口**：Issues 列表。

勾选需要一起处理的记录，或“全选待审”。确认已选数量后点击 **“统一审核 N 个 Issues”**。AI 联合分析这些 Issue 之间，以及它们与正式需求、任务包之间的冲突。

选定批次被冻结，未选中与后来提交的 Issue 留到下一批。分析根据需求与任务包，不要求先收集代码证据或全员在线。受影响的未完成任务暂停，其余任务继续开发。

CLI 可指定真实内部变更 ID：

```powershell
vibe-git agile review <pr-id-1> <pr-id-2>
vibe-git agile wait <flow-id> 600
```

不传 PR ID 会纳入本阶段待审记录；需要选择批次时明确传 ID，或使用网页勾选。

**成功结果**：所选记录进入同一审核，页面显示分析与影响任务。**失败处理**：按钮禁用时检查选择数量、当前审核和队长身份；功能未加载提示时先在作业结束后重启新版服务。**下一步**：处理冲突与裁决。

## 步骤 3：裁决并生成新版需求

> **操作人**：队长。**前置条件**：分析结果返回。**入口**：Issues 的本批审核区域。

1. 按问题选择 A/B/C，或 **“我有自己的方案”**，点击 **“确认并继续”**。
2. 在逐项结论中核对每条 Issue，选择 **“采纳”** 或 **“退回”**，填写裁决原因。
3. 阅读影响任务列表，确认完成任务是否需要后续修订。
4. 点 **“确认审核并生成需求”**；已经生成后修改裁决时，点 **“确认审核并重新生成”**。
5. 全部退回时使用 **“确认全部退回”**，不产生空的新需求版本。

**成功结果**：采纳内容生成完整新版需求草稿；全部退回则本批结束，原任务恢复。**失败处理**：存在未处理冲突时先裁决；修改结论后旧草稿和分工会失效，必须重新生成。**下一步**：到 Wiki 编辑新版草稿。

## 步骤 4：核对差异并重新派发

> **操作人**：队长。**前置条件**：新版需求草稿已生成。**入口**：Wiki → 当前草稿，随后 Projects → 分工审核。

按[需求与派发教程](./dispatch.md)编辑、保存、生成分工。逐项阅读目标、边界、验收的前后差异，核对：

- 受影响未完成任务的实质修订；只换版本标识不能代替修改任务内容。
- 未受影响任务的负责人和进度继续保留。
- 已完成任务需要返工时生成关联后续任务，原完成记录保留。
- 撤销任务会归档，不再继续原目标。

需求编辑过程中新增的影响也会在分工前重新核对。最后点击 **“派发任务包”**，新版正式需求与整批任务包共同发布，全员收到更新。

**成功结果**：Wiki 出现正式 R2（或实际下一版本），任务修订与通知同步。**失败处理**：修订被拒绝时保留需求草稿，检查是否真正改变目标、边界、验收，再重试分工。**下一步**：成员[核对新版本](./execution.md#revisions)后继续。

## 步骤 5：取消、退回或重试

> **操作人**：队长。**前置条件**：存在未结束的本批审核。**入口**：审核区域的更多操作，或失败状态的“重试”。

| 操作 | 使用时机 | 结果 |
| --- | --- | --- |
| 取消审核，恢复原任务 | 暂不处理本批，稍后再选 | Issue 回队列，原任务恢复 |
| 退回整批 Issue | 明确不采纳本批 | 本批退回，原任务恢复，不发布空版本 |
| 重试 | 分析失败，原因已修复 | 保留回答和草稿，重试当前阶段 |

CLI 对应 `agile cancel/reject/retry <flow-id>`，每次只执行你决定的那一种操作。

**成功结果**：状态与所选操作一致；失败重试后继续同一流程。**失败处理**：版本过期先刷新本批状态，已派发记录不能当作未完成审核取消。**下一步**：继续本批或选择下一批。
