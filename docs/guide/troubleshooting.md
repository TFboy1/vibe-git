# 问题处理

先保留草稿、报告与原始错误，再处理对应问题。日志需要转发时仅提供相关错误，去掉邀请密钥、节点凭据和 API Key。

## 步骤 1：安装失败或缺少新版命令

> **操作人**：安装者。**前置条件**：环境检查、构建或命令帮助异常。**入口**：本机 PowerShell。

1. `node --version` 确认 ≥ 24。
2. `Get-Command vibe-git -All` 检查是否调用了旧安装。
3. 确认处于 `codex/frontend-rebuild` 分支的内层 `vibe-git` 目录。
4. 依次重做 `npm.cmd ci`、`npm.cmd run build`、`npm.cmd link`。
5. 重开终端，检查帮助的“超敏捷主线”。

“Missing script: build”先检查目录；PowerShell 提示不能运行 npm 脚本时使用 `npm.cmd`；依赖下载错误按实际网络或 npm 错误修复。

**成功结果**：构建成功，新版命令可用。**失败处理**：保留第一处构建错误，不跳过失败直接链接。**下一步**：重新做[能力检查](./install.md#capability-check)。

## 步骤 2：邀请失效或连接恢复中

> **操作人**：队长与受影响成员。**前置条件**：`connect` 失败或页面断线。**入口**：各自本机终端。

成员执行 `vibe-git status`、`vibe-git logs`。队长执行 `vibe-git host status`、`vibe-git invite show`，确认服务和当前 Tunnel。成员使用当前完整邀请与自己的项目路径，再从本机 `open` 进入。

**成功结果**：状态显示正确房间，页面恢复同步。**失败处理**：仍失败时核对完整 URL、网络、进程和磁盘空间；不删数据库或本机草稿来“修复”。**下一步**：Skill 同步收件箱。

## 步骤 3：页面只读、按钮缺失或无权限

> **操作人**：页面使用者。**前置条件**：无法编辑自己的计划，或看不到管理按钮。**入口**：终端与 Settings。

从本人电脑运行 `vibe-git open`，用 `status` 检查 `node.role` 与节点 ID。成员不会显示队长的整合、审核、派发入口，其他成员计划也只读。正式需求版本只读，队长应选择当前草稿才能编辑。

**成功结果**：在正确身份和版本下操作。**失败处理**：新版 CLI 已构建但旧服务仍运行时，由队长在作业结束后重启正确项目，再刷新页面。**下一步**：回到相应教程。

## 步骤 4：算力不可用或 API 测试失败

> **操作人**：队长；本机登录由本人完成。**前置条件**：分析前算力不可用。**入口**：Settings → 算力与 API、Codex 连接与额度。

Codex 路径先完成本人授权、刷新节点状态，确认在线可用节点。API 路径检查 Base URL 是否正确包含服务需要的 `/v1`，且末尾没有 `/responses`；核对模型、Key、Responses 和 JSON Schema 支持，再“保存并测试连接”。

**成功结果**：配置可用，测试通过。**失败处理**：按测试具体错误修复，不把单纯保存当作通过，不把额度未知理解为零。**下一步**：启动或重试分析。

## 步骤 5：分析失败或等待超时 {#analysis-failed}

> **操作人**：队长。**前置条件**：流程显示“本次分析未完成”或 `agile wait` 超时。**入口**：当前流程的错误状态。

先读错误，修复算力、服务连接或输出问题，再点 **“重试”**；CLI 使用 `agile retry <flow-id>`。回答与需求草稿会保留。等待超时后继续 `agile wait <flow-id> 600`，不用重新创建整个流程。

**成功结果**：同一流程继续，出现待裁决问题或草稿。**失败处理**：重复失败时保留流程 ID 和具体错误，反馈问题，不用高频查询代替修复。**下一步**：按当前状态继续裁决、编辑或分工。

## 步骤 6：需求草稿冲突或分工失效

> **操作人**：队长。**前置条件**：另一个窗口更新草稿，或编辑后分工不可派发。**入口**：Wiki。

先 **“导出 MD”** 保存本机未保存内容，再核对服务器最新版本，合并需要保留的段落。确认不需要本机草稿时才使用“舍弃本机草稿，恢复服务器版本”。等待正文保存，再重新生成分工。

**成功结果**：完整正文已保存，新分工对应当前草稿。**失败处理**：保存仍冲突时停止多窗口并行编辑，刷新最新版本后再合并。**下一步**：[审核分工](./dispatch.md)。

## 步骤 7：任务报告版本过期或完成被拒绝

> **操作人**：任务负责人。**前置条件**：`task report` 报错。**入口**：任务包与报告文件。

检查真实任务 ID、负责人、任务是否暂停／归档、前置依赖、完成证据和执行版本。新版已经发布时保留旧报告，阅读需求与任务差异，决定补做内容；不能只把数字改新后重交。完成必须附非空真实 `evidence`。

**成功结果**：报告与实际执行版本一致，条件满足后成功提交。**失败处理**：暂停且未有新包时由队长检查审核；证据不足先完成验证。**下一步**：[处理修订](./execution.md#revisions)。

## 步骤 8：任务包导出提示文件已存在

> **操作人**：导出者。**前置条件**：指定输出文件已存在。**入口**：产品工作区终端。

换一个包含实际版本或日期的文件名再执行 `task package`，或不指定输出文件直接读取结构化任务包。CLI 会保护已有文件，不覆盖它。

**成功结果**：新任务包导出，旧文件保留。**失败处理**：路径权限错误时换到本人可写目录。**下一步**：阅读当前包，再开发或汇报。
