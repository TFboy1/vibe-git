# 整合计划与裁决

## 步骤 1：启动本轮整合

> **操作人**：队长。**前置条件**：本轮计划已收齐或明确跳过，团队算力可用，尚未发布首轮需求。**入口**：Code → 个人计划。

点击 **“整合本轮计划”**。系统冻结本轮参与者的计划版本，开始分析共同目标、差异和实质冲突。成员查看原始计划与分析结果，由队长决定冲突处理方式。

**成功结果**：页面出现“正在分析需求与冲突”等进度。**失败处理**：等待计划时回到[计划收集](./plans.md)；算力错误时检查[配置](./compute.md)。**下一步**：等待分析。

## 步骤 2：等待结果

> **操作人**：队长。**前置条件**：整合已成功启动。**入口**：个人计划页的流程状态；也可使用 CLI。

可以留在页面，也可以稍后返回，已提交的内容会保留。CLI 使用真实流程 ID 阻塞等待：

```powershell
vibe-git agile list
vibe-git agile wait <flow-id> 600
vibe-git agile show <flow-id>
```

`<flow-id>` 来自启动回执或 `agile list`，不能用任务 ID 代替。`wait` 最多等待 600 秒；结果需要你处理时会返回，并不一定意味着整个流程已完成。超时后作业和草稿保留，可继续等待同一流程。

**成功结果**：出现冲突问题，或没有冲突时直接生成需求草稿。**失败处理**：状态为失败时查看错误并点击“重试”，不频繁查询或重复启动。**下一步**：有冲突执行步骤 3，无冲突进入步骤 4。

## 步骤 3：逐项确认冲突

> **操作人**：队长。**前置条件**：流程正在等待裁决。**入口**：个人计划页的“冲突裁决”。

1. 阅读问题原因及原始计划引用，确认到底是哪两种目标发生冲突。
2. 每题从 **A、B、C** 三个方案中选择一个，并阅读影响说明。
3. 需要自己的方案时选 **“我有自己的方案”**，填写具体处理决定。
4. 点击 **“确认并继续”**，等待重新分析。
5. 继续处理下一题。必要时会有追问，已确认裁决可在下方历史中查看。

例如，接口是否支持删除尚有分歧，可以决定“本轮仅新增和完成，删除留到后续需求变更”，并说明这一决定对页面与接口的影响。

**成功结果**：问题记录回答，后续问题或需求草稿出现。**失败处理**：按钮不可用时先选择方案；自定义答案不能为空；版本发生变化时先读当前问题，不提交过期答案。**下一步**：确认共同需求。

## 步骤 4：打开共同需求草稿

> **操作人**：队长。**前置条件**：所有必要裁决结束，完整需求已生成。**入口**：个人计划页 **“查看需求文档”**，或 Wiki。

阅读需求正文，检查目标、范围、验收和裁决是否被完整保留。此时是可编辑的草稿，还没有向成员发布正式任务。

**成功结果**：Wiki 显示共同需求草稿，队长可以编辑。**失败处理**：草稿缺失时查看当前流程是否仍在分析；失败则修复原因后重试。**下一步**：[编辑需求、分工与派发](./dispatch.md)。

## 全程使用 CLI 时

队长 `vibe-git agile start` 启动整合，随后通过 `list/wait/show` 读取真实流程。回答 JSON、保存草稿和分工命令见 [CLI 参考](./reference.md#agile-cli)。CLI 和网页操作同一流程，不要同时重复启动。
