# 每人提交计划

第一轮由每位参与者写下自己的目标、范围和方案。队长的计划同样需要提交，个人计划不会自动变成共同需求。

## 步骤 1：进入自己的计划

> **操作人**：队长和成员。**前置条件**：已连接房间并从本机打开工作台。**入口**：Code → 个人计划 → 我的计划。

没有计划时点击 **“开始创建计划”**。已经有内容时直接编辑正文。其他成员的计划可以查看，不能替代所有者修改。

**成功结果**：编辑的是本人计划，页面显示“待提交”或已有版本。**失败处理**：正文只读时重新执行本机 `vibe-git open`，检查选中的是否是其他成员计划。**下一步**：写清方案。

## 步骤 2：编写或导入 Markdown

> **操作人**：计划所有者。**前置条件**：本人编辑入口可用。**入口**：计划正文，或 **“导入 MD”**。

直接在正文编辑，也可以导入非空 UTF-8 `.md` 文件，文件不超过 256 KiB。建议包含这些内容：

````markdown
# 我的第一轮计划

## 目标
完成团队待办板的 Vue 页面，支持新增、完成和查看待办。

## 当前项目
写明已经有的页面、接口与目录，以及哪些能力尚未实现。

## 方案与范围
负责页面、状态显示和接口调用。
接口字段与错误格式先由团队统一，不自行改变后端协议。

## 验收标准
- 能查看待办列表、新增待办、切换完成状态。
- 请求失败时显示具体错误，保留用户输入。
- 前端生产 build 通过。

## 风险与需要确认的事
需要确认接口字段、排序规则与删除功能是否属于本轮。
````

模板只用于说明结构。替换为真实项目目标与验收；队长可写后端或整体方案。保存到本机的草稿不代表队友已经看到。

**成功结果**：内容包含明确目标、范围与验收。**失败处理**：导入报错时检查 `.md` 扩展名、UTF-8 编码和大小；页面保留的草稿可先“导出 MD”备份。**下一步**：提交。

## 步骤 3：提交并确认版本

> **操作人**：计划所有者。**前置条件**：正文非空，内容已经本人确认。**入口**：编辑区底部。

1. 首次点击 **“提交计划”**，后续修订点击 **“更新计划”**。
2. 等待成功反馈，确认标签显示 **“已提交 · v…”**。
3. 查看其他成员的计划标签，确认能够读取团队已经提交的方案。

CLI 可在产品工作区提交文件：

```powershell
vibe-git plan submit .\my-plan.md
```

同一节点再次提交更新自己的计划，不会产生第二个成员。CLI 回执成功后再报告已提交。

**成功结果**：新版本在房间可见，不再显示有未提交修改。**失败处理**：版本冲突时导出本机草稿，读取最新版本后合并内容，再提交；不直接覆盖别人的更新。**下一步**：队长检查收集情况。

## 步骤 4：收齐本轮参与者

> **操作人**：队长。**前置条件**：参与者已经提交或明确暂不参与。**入口**：个人计划右侧的团队列表。

检查每个人是否显示“计划已提交”。对本轮确实不参与且尚未提交的人，明确勾选 **“本轮暂不参与”**。未收齐且未跳过的成员会让整合按钮不可用。

**成功结果**：计划收齐，**“整合本轮计划”** 可以执行。**失败处理**：仍有等待计划的人时，请其提交，或明确决定本轮跳过；不能全部跳过。**下一步**：[整合计划与裁决](./alignment.md)。

::: tip 正式需求发布之后
个人计划作为原始想法保留。改变已发布需求时，去 Issues [提出需求变更](./changes.md)，而不是修改计划后认为正式需求已经更新。
:::
