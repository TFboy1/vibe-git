# 补充想法（可选）

新版默认从队长的一份简述目标开始。队长在“需求”页输入目标或导入已有文档；成员可以补充想法，也可以只负责执行。至少一份有效输入即可启动，不需要全员提交完整计划。输入在发布前不等于正式需求。历史房间首轮仍按[历史流程](./legacy.md)操作。

## 步骤 1：进入自己的计划

> **操作人**：按需提出意见的队长或成员。**前置条件**：已连接房间并从本机打开工作台。**入口**：需求 → 可选想法 → 我的想法。

直接写下你的想法或编辑已有内容。可以查看其他成员已提交的想法，不能替代所有者修改。需求起步与可选想法共用本人草稿，切换页面会保留输入。

**成功结果**：编辑的是本人输入，页面显示“可选提交”或已有版本。**失败处理**：正文只读时重新执行本机 `vibe-git open`，检查选中的是否是其他成员。**下一步**：编写建议或导入已有文档。

## 步骤 2：编写或导入 Markdown

> **操作人**：计划所有者。**前置条件**：本人编辑入口可用。**入口**：计划正文，或 **“导入 MD”**。

可以只写一句建议，例如“第一轮先支持新增和完成待办，删除以后再做”。也可以导入非空 UTF-8 `.md` 文件，文件不超过 256 KiB。已有完整计划可以使用以下结构，但不是必填模板：

````markdown
# 我的第一轮计划

## 目标
完成团队待办板的 Vue 页面，支持新增、完成和查看待办。

## 当前项目
写明已经有的页面、接口与目录，以及哪些能力尚未实现。

## 方案与范围
负责页面、状态显示和接口调用。
接口字段与错误格式先由团队统一，不自行改变后端协议。

## 验收标准
- 能查看待办列表、新增待办、切换完成状态。
- 请求失败时显示具体错误，保留用户输入。
- 前端生产 build 通过。

## 风险与需要确认的事
需要确认接口字段、排序规则与删除功能是否属于本轮。
````

模板只用于说明结构。替换为真实项目目标与验收；队长可写后端或整体方案。保存到本机的草稿不代表队友已经看到。

**成功结果**：记录了真实目标或建议。关键范围与验收缺口由 AI 在问答中补齐。**失败处理**：导入报错时检查扩展名、UTF-8 编码和大小；可先“导出 MD”备份本机草稿。**下一步**：提交。

## 步骤 3：提交并确认版本

> **操作人**：计划所有者。**前置条件**：正文非空，内容已经本人确认。**入口**：编辑区底部。

1. 首次点击 **“提交想法”**，后续修订点击 **“更新想法”**。
2. 等待成功反馈，确认标签显示 **“已提交 · v…”**。
3. 查看其他成员的计划标签，确认能够读取团队已经提交的方案。

CLI 可在产品工作区提交文件：

```powershell
vibe-git plan submit .\my-plan.md
```

同一节点再次提交更新自己的计划，不会产生第二个成员。CLI 回执成功后再报告已提交。

**成功结果**：新版本在房间可见，不再显示有未提交修改。**失败处理**：版本冲突时导出本机草稿，读取最新版本后合并内容，再提交；不直接覆盖别人的更新。**下一步**：队长检查收集情况。

## 步骤 4：队长选择何时汇总

> **操作人**：队长。**前置条件**：至少一份有效目标或想法、协作算力可用、没有进行中的流程。**入口**：需求页“生成需求”，或可选想法页顶部的汇总按钮。

阅读已提交输入，决定是否开始分析。没有提交意见的成员不会阻塞，也不需要勾选跳过；他们仍可以成为任务负责人。开始后冻结本轮来源，后来更新的意见留到下一轮。

**成功结果**：开始需求分析；已有正式需求时，“汇总本轮想法”会进入统一的变更审核批次。**失败处理**：按钮旁显示输入、算力或活动流程的问题；本机版本冲突时先导出，再核对或恢复已提交内容。**下一步**：[补齐需求与确认方案](./alignment.md)。

::: tip 正式需求发布之后
原始想法保留。队长可以按需汇总本轮已提交输入，基于当前正式版本审核并生成新版草稿；单项调整也可以去“变更”[提出需求变更](./changes.md)。提交或修改想法本身不会更新正式需求。
:::
