# 开发与任务汇报

::: tip 新版成员的操作方式
成员无需网页领取、开工确认或修订确认。通过当前开发 Agent 的 Skill 同步任务包、执行用户要求的开发、提交报告；不使用旧版 `task start/sync/done` 代替新版汇报。
:::

## 步骤 1：同步并读懂本人任务包

> **操作人**：任务负责人及当前 Agent。**前置条件**：队长已派发，本人已连接。**入口**：产品工作区终端或 Skill。

```powershell
vibe-git task inbox
vibe-git task package <task-id>
```

从收件箱的 `tasks` 中取得本人真实任务 ID，查看 `package.taskId`、`package.taskRevision`、`package.requirementRevision`、完整需求、验收、边界、依赖和 `nextStep`。需要 Markdown 文件时：

```powershell
vibe-git task package <task-id> .\task-package-v1.md
```

输出文件不能重名，CLI 不覆盖已有文件。每次 Skill 调用先读 `inbox`，优先处理暂停和版本修订；任务暂停时停止旧版本工作，上游未完成时遵循任务包的等待说明。

**成功结果**：读到本人真实任务包和执行版本。**失败处理**：收件箱为空时检查负责人、本人节点和派发状态；无权读取时不要用其他人的任务 ID。**下一步**：开始当前用户要求的工作。

## 步骤 2：向当前 Agent 说明任务

> **操作人**：任务负责人。**前置条件**：已阅读任务包且没有暂停、依赖等阻塞。**入口**：当前产品工作区的 Agent 会话。

> 请使用 vibe-git Skill，先同步收件箱并读取我的任务包。确认真实任务 ID、任务包版本、需求版本、目标、边界和验收后，执行我本次要求的开发，并汇报开工。发现任务暂停或修订时先说明变化，不继续旧版本目标。

Agent 应保存本次实际读取的版本，并通过 `task report` 汇报 `started`。同步收件箱只负责读取状态，不会自动授权另一个开发任务或启动独立 Agent 会话。

**成功结果**：开工汇报成功，任务进入相应开发状态。**失败处理**：任务被暂停、归档或版本过期时重新核对任务包；不能只把报告版本号改为最新值。**下一步**：记录进展或阻塞。

## 步骤 3：汇报进度与阻塞

> **操作人**：当前任务负责人。**前置条件**：已有实际开发进展或阻塞。**入口**：Skill；手动时在产品工作区保存 UTF-8 JSON。

报告模板：

```json
{
  "reportId": "本次汇报的唯一标识",
  "taskRevision": 1,
  "requirementRevision": 1,
  "action": "progress",
  "summary": "说明实际完成的内容、当前进度和下一步",
  "evidence": []
}
```

`1` 是示例，必须替换为本次**实际读取并执行**的任务包版本。`reportId` 每次新报告使用新标识；重试同一份报告保留原标识和内容，可以用 `[guid]::NewGuid().ToString()` 生成。

| action | 使用时机 | summary 写什么 |
| --- | --- | --- |
| `started` | 已读取执行包，开始本次工作 | 当前目标和执行版本 |
| `progress` | 取得阶段进展 | 已完成内容、剩余工作 |
| `blocked` | 无法继续 | 具体原因、需要谁提供什么 |
| `completed` | 目标与验收实际完成 | 交付结果与验证证据 |

保存为例如 `report-progress.json` 后执行：

```powershell
vibe-git task report <task-id> .\report-progress.json
```

**成功结果**：CLI 返回成功，Projects 显示新的进度或阻塞说明。**失败处理**：JSON 错误先修格式；版本冲突保留报告与证据，重新读取修订并决定需要补做什么。**下一步**：继续工作，或完成验收后提交完成报告。

## 步骤 4：带证据汇报完成

> **操作人**：任务负责人。**前置条件**：目标和验收已完成，依赖完成，任务未暂停；仍使用真实执行版本。**入口**：Skill 或 `task report`。

完成报告模板：

```json
{
  "reportId": "本次完成报告的唯一标识",
  "taskRevision": 1,
  "requirementRevision": 1,
  "action": "completed",
  "summary": "替换为实际交付结果及验收结论",
  "evidence": [
    "替换为实际验证命令、退出码和结果",
    "替换为另一个已完成验收项及其证据"
  ]
}
```

不能提交模板占位文字作为真实证据。证据可以是实际 build、后端测试或人工验收的具体结果；没有运行的检查不要写“通过”。完成报告的 `evidence` 必须非空。

```powershell
vibe-git task report <task-id> .\report-completed.json
```

**成功结果**：系统记录 `DONE`，无需网页再次确认。**失败处理**：依赖未完成、缺少证据、暂停或版本冲突时，先处理对应原因，不用旧 `task done` 绕过。**下一步**：[代码提交与 PR](./git.md)，或处理新的需求变更。

## 步骤 5：处理新版本与暂停消息 {#revisions}

> **操作人**：每位受影响任务负责人。**前置条件**：队长正在审核或已派发修订。**入口**：下一次 Skill 调用、收件箱与 Projects。

先读暂停消息，停止旧版本目标；新版发布后阅读修订摘要、完整需求、目标、边界和验收差异，再按用户本次指令继续。旧结果的报告被拒绝时保留证据，核对是否需要返工，不能给旧结果补填最新版本号重交。

**成功结果**：执行内容与实际版本一致。**失败处理**：暂停后迟迟没有新版时请队长查看本批审核，确认继续、取消或退回。**下一步**：新版开工或进度汇报。
