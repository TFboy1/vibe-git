# 需求、分工与派发

## 步骤 1：编辑完整需求

> **操作人**：队长。**前置条件**：[计划整合](./alignment.md)已生成草稿。**入口**：Wiki → 当前需求草稿。

1. 阅读完整正文，核对本轮目标、范围、接口约定和验收。
2. 点击正文直接编辑；需要替换文件时用 **“导入 MD”**，备份时用 **“导出 MD”**。
3. 等待 **“已保存 · 草稿 v…”**；有待保存修改时可点 **“立即保存”**。
4. 查看版本选择器，可阅读草稿历史和正式需求历史。

成员可读取草稿，但不能代替队长编辑。正式版本只读，要修改时走需求变更。

**成功结果**：正文准确且显示已保存。**失败处理**：另一个窗口更新需求时先导出本机草稿，核对服务器版本后再合并；不要丢掉本机修改。**下一步**：生成分工。

## 步骤 2：生成分工

> **操作人**：队长。**前置条件**：正文已保存，算力可用。**入口**：Wiki 底部 **“生成分工”**。

点击生成，等待“正在生成任务分工”。完成后点 **“审核分工”**，进入 Projects。CLI 等待同样使用 `agile wait`，真实流程 ID 从 `agile list` 取得。

修改需求会使已有分工草稿失效。如果生成后再次改正文，必须重新生成；不要派发基于旧正文的分工。

**成功结果**：分工草稿就绪，可以在 Projects 审核。**失败处理**：生成失败保留需求草稿，修复算力或输出问题后重试；正文仍在保存时先等待。**下一步**：核对每项任务。

## 步骤 3：核对并调整分工

> **操作人**：队长。**前置条件**：当前分工草稿已生成。**入口**：Projects → 任务看板中的分工审核。

点击任务标题展开，逐项检查：

| 字段 | 必须确认的内容 |
| --- | --- |
| 负责人 | 是本轮预期成员，名字重复时核对节点 ID |
| 具体目标 | 说明应交付什么，不只写“完成开发” |
| 职责边界 | 指定负责内容和与其他任务的交接关系 |
| 验收要求 | 每行一项，能判断完成与否 |
| 负责／排除路径 | 已知时使用项目相对路径，防止互相覆盖 |
| 前置依赖 | 指向真实上游任务，不能依赖自身或形成环 |
| 需求引用 | 与本轮需求章节或原文一致 |

需要批量调整负责人时，勾选任务，选择负责人，点击 **“分配选中任务”**。可以添加任务，移除不需要的新任务。修改后点击 **“保存调整”**。

**成功结果**：分工覆盖需求且没有范围、负责人或依赖错误，修改已保存。**失败处理**：字段或依赖错误按反馈修正；发现需求本身要变时回到 Wiki 编辑并重新生成。**下一步**：统一派发。

## 步骤 4：发布正式需求与任务包

> **操作人**：队长。**前置条件**：完整需求和分工均已核对。**入口**：分工审核底部 **“派发任务包”**。

点击派发，等待成功反馈。首轮需求 R1 与整批任务包在同一事务中发布。发布后：

1. Wiki 显示正式需求版本。
2. Projects 可以查看已派发任务、负责人和状态。
3. 成员任务收件箱收到自己的任务包及通知。

成员无需在网页领取、确认开工或确认修订。实际开发由成员当前 Agent 读取任务包后执行，不会因为队长派发就自动开启新的开发会话。

**成功结果**：正式版本与任务包均可查到。**失败处理**：派发报错时保留草稿并刷新真实状态，确认是否已发布后再处理，避免重复操作。**下一步**：[开发与任务汇报](./execution.md)。

## 步骤 5：成员确认执行依据

> **操作人**：每位任务负责人。**前置条件**：队长已派发。**入口**：Projects → 任务包；或当前 Agent 的 Skill。

查看本人任务目标、验收、依赖、任务包版本和需求版本。用 `vibe-git task inbox` 同步，再把真实任务包交给当前 Agent。无法确认版本时先同步，不自行猜填。

**成功结果**：负责人读到当前正式任务包。**失败处理**：收件箱为空时确认本人节点、负责人分配及派发结果。**下一步**：按任务包开发并汇报。
