# Vibe-Git 用户流程改造实施计划

日期：2026-10-13  
状态：待实施。本轮只记录计划，尚未修改功能代码。

## 目标与已确认的决定

面向已经用 AI 开发、懂基本 Git 的小团队。成员继续在现有开发 AI 中工作，网页负责展示状态、收集团队决定，以及把具体任务交给开发 AI。

用户的默认路径：

```text
队长简述目标，成员按需补充想法
  → AI 以选择题和自定义输入补齐关键缺口
  → 生成可编辑的需求草稿
  → 生成并预览分工
  → 队长一次发布正式需求与任务包
  → 成员复制当前任务指令，交给现有开发 AI
  → Skill 同步真实任务版本并汇报
  → 附验收证据汇报完成
```

开发中提出需求变更后，AI 联合分析选中的变更，自动请求暂停受影响的未完成任务。队长确认新版需求和分工后统一发布。已完成任务受到影响时创建关联后续任务，保留原完成与验证记录。

## 当前实现与需要改变的地方

| 事项 | 当前事实 | 实施处理 |
| --- | --- | --- |
| 初始输入 | 个人计划页要求填写目标、范围和验收；需求页在整合前为空 | 把默认起点放到需求页，允许短描述或 Markdown 导入 |
| 计划收集 | `AgileService.collectPlans()` 被首轮整合和新一轮计划整合共同调用，默认要求全员有计划 | 在共享入口改为收集有效的已提交输入，至少一份；其他成员不再阻塞 |
| AI 追问 | `AGILE_ANALYZE` 目前仅允许询问真实冲突，`AGILE_DIALOGUE` 仅检查新矛盾 | 首轮增加关键需求缺口的追问；变更审核继续限制在选中批次 |
| 可分配成员 | 分工已经允许所有未撤销成员成为负责人，不要求他们提交计划 | 复用现有校验，增加无计划成员接任务的后端覆盖 |
| 导航与首页 | GitHub 风格导航，默认首页是团队成员与 Git 状态 | 主导航使用业务名称，首页按队长/成员突出当前行动 |
| 初始问答 | 目前在个人计划页，已有三方案和自定义输入的 `PlanWizard` | 首轮问答放到需求页，复用组件与原状态机 |
| 发布 | 后端已经在同一事务中发布需求和任务包 | 保留一个正式发布确认关口 |
| 任务执行 | 任务页只有查看、导出与泛化的 Skill 提示 | 增加当前任务专属的可复制指令，明确下一步 |
| 暂停 | Host 将任务标为暂停并禁止旧版本汇报；开发 AI 下次调用 Skill 时才读取消息 | 页面写明“已请求暂停”和同步时机，准确表达执行边界 |
| 完成与返工 | 附证据汇报后完成，已完成来源任务的修订生成关联新任务 | 复用现有行为，增强完成记录与后续任务的说明 |

保留 Vue 与当前 Fastify/SQLite 后端，以及现有 Host、CLI、Relay、认证和持久化机制。本轮重点在入口、共享业务门槛、AI 提问规则与状态说明；现有分工、联合发布、版本校验、任务汇报和返工能力继续复用。

## 实施顺序

### 0. 确认基线

- 以当前工作区为基线，保留已有未提交修改；逐个阅读将修改的函数及全部调用者。
- 先记录现有后端测试与构建结果，再开始修改，区分既有问题和本次回归。
- 使用现有数据库、API 和协议类型；不清理房间数据，不自动重启用户正在使用的 Host。

### 1. 跑通“一份简述生成需求”

**涉及文件**：

- `apps/host/src/v20/agile-service.ts`
- `apps/host/test/agile.test.ts`
- `apps/web/src/views/RequirementsView.vue`
- `apps/web/src/views/RoomView.vue`
- `apps/web/src/store.ts`
- `apps/web/src/components/PlanWizard.vue`（只在必要时调整文案）

**改法**：

1. 在需求页未发布首轮需求的状态下，给队长提供“简述目标 / 导入 Markdown”入口，普通成员看到可选补充想法的入口。
2. 初始描述复用现有计划文档提交能力，作为 AI 的输入来源；若本人已有内容，加载为编辑起点，使用现有 `expectedRevision` 更新并保留历史，不静默覆盖。
3. 提交与启动分析的共同操作放在现有 store 中供需求页和个人计划页调用；先保存有效输入，再启动分析。分析启动失败时，已保存输入仍可编辑或重试。
4. 修改 `collectPlans()`：收集未撤销成员已经提交且未撤回的最新文档；无计划成员不再阻塞。没有任何有效输入时拒绝启动。保留现有跳过参数的合法性检查，兼容仍传该参数的 CLI/API 调用。
5. 同时覆盖 `startInitial()` 和 `startPlanIntegration()`，保持队长权限、单一活动流程、需求版本校验与来源冻结。
6. 首轮 AI 分析允许询问阻碍形成可执行需求的关键缺口和真实冲突；信息足够就生成草稿。追问不能重复已回答事项，也不能把未决定的内容当作已确认要求。
7. 继续复用现有每题三个有意义方案、自定义答案、结构化输出校验和草稿历史。开发中审核仍只处理本批选中的变更，后来提交的内容留到下一批。
8. 将首轮 `PlanWizard` 与 `FlowStatus` 放到需求页；个人计划页保留可选想法的编写、查看和提交能力，通过链接回到当前需求流程。开发中变更问答仍留在变更页。

**后端检查**：

- 队长只提交一份短描述，成员未提交计划，仍能生成需求、分工并给该成员派任务。
- 完全无输入、输入已撤回或所有有效来源被排除时不能启动。
- 非队长、过期需求版本、重复活动流程仍被拒绝。
- 开始后新增或修改的想法不会改变本轮冻结来源。
- 首轮追问经过回答后进入需求草稿；已有信息充分时可以直接进入草稿。
- 已有正式需求的新一轮整合仍走审核流程，取消、算力失败和来源复用行为保持正确。

**阶段结果**：即使尚未调整首页，用户也能从需求页完成“短描述 → 选择题 → 需求草稿 → 分工 → 发布”。

### 2. 调整导航与角色首页

**涉及文件**：

- `apps/web/src/App.vue`
- `apps/web/src/router.ts`
- `apps/web/src/views/CodeView.vue`
- `apps/web/src/store.ts`、`apps/web/src/team.ts`（按实际复用需求调整）

**改法**：

1. 主导航收敛为“工作台、需求、任务、变更、设置”。保留现有路径，更新显示名称和路由标题。
2. 个人计划改为需求下的可选输入入口；自由 AI 分析和代码 PR 从相关业务页面进入，原路由与已有链接仍可访问。
3. 首页首先显示当前角色需要做的事情。团队成员、分支、提交等信息保留在下方，作为了解团队进度的辅助信息。
4. 复用现有流程状态、任务、依赖和算力状态计算当前行动；相同判断有多个调用者时才放入现有 store/helper，避免另建一套状态机。
5. 当前阶段与下一步入口在相关流程页面保持可见，进入需求、任务或变更页后仍能理解自己所处阶段。

队长首页的主要行动：

| 状态 | 首页提示与入口 |
| --- | --- |
| 无正式需求、无活动流程 | 创建需求，进入简述目标 |
| 分析或生成中 | 显示真实进度、保留内容的说明与所在流程入口 |
| 等待回答 | 首轮进入需求页回答；审核阶段进入变更页处理 |
| 需求草稿可编辑 | 审核正文并生成分工 |
| 分工就绪 | 检查负责人、目标、边界、验收和依赖，再统一发布 |
| 开发中有待审变更 | 查看并选择要审核的变更批次 |
| 失败或缺少算力 | 显示原因，提供原流程重试或对应设置入口 |

成员首页显示本人任务与待同步变化，说明“现在做什么 / 为什么等待 / 在等谁”。依赖未完成、任务暂停、尚未派发和任务已完成分别给出准确说明，避免把所有情况都写成等待分配。

**阶段结果**：队长能够直接推进当前环节；成员能够找到自己的当前任务及等待原因。

### 3. 补齐任务到开发 AI 的交接

**涉及文件**：

- `apps/web/src/views/TasksView.vue`
- `apps/web/src/views/AgentsView.vue`（仅相关入口与说明）
- `apps/web/src/team.ts`（仅共享状态文案）

**改法**：

1. 在本人任务详情提供“复制给开发 AI”操作，复用现有剪贴板写入方式；复制失败时展示可手动复制的文本。
2. 指令包含真实任务 ID、任务标题及本次操作意图，要求先调用 Skill 读取收件箱，处理暂停/修订，取得最新任务包，再执行用户要求的工作。
3. 任务 ID 是定位信息，复制时页面展示的版本不作为执行版本授权；实际汇报必须继续使用 AI 已读取并执行的版本，保留后端过期版本拒绝规则。
4. 暂停或存在未完成依赖时，交接说明优先同步与等待，不能提示直接开工。
5. 页面解释由 Skill 处理开工、进度、阻塞和完成汇报；用户不需要手动维护 JSON、版本号或另做网页完成确认。
6. 工作台内的自由 AI 对话明确是分析建议，正式团队操作仍从业务页执行，开发交给现有开发 AI。

**阶段结果**：成员打开一个任务，能得到针对该任务的具体指令，无需自己猜怎样调用 Skill。

### 4. 收尾变更、完成与返工说明

**涉及文件**：

- `apps/web/src/views/ChangesView.vue`
- `apps/web/src/views/TasksView.vue`
- `apps/web/src/components/TaskAllocation.vue`
- `apps/host/test/agile.test.ts`（按已有覆盖补充必要回归）
- `docs/AGILE-WORKFLOW.md` 与根目录 `docs/guide/` 中涉及计划、对齐、执行和派发的教程

**改法**：

1. 将暂停说明统一为“已请求暂停，开发 AI 下次调用 Skill 时读取”，不能把 Host 状态或通知已读当成 AI 已实际停止的证明。
2. 明确展示受影响任务与未受影响任务的处理结果；保留取消审核恢复任务、失败重试、草稿保存与版本漂移拒绝能力。
3. 已完成任务受影响时，在分工预览及新任务详情展示关联来源和本次需要补做的内容，保留原完成与验证记录。
4. 成员附有效验收证据汇报完成后直接完成；代码 PR 的状态、审查和合并继续由原 Git 托管平台维护。
5. 同步教程中的默认入口、个人计划可选、任务交接和暂停时机；保留历史流程说明的明确边界。

**后端回归关注点**：

- 只暂停受影响的未完成任务，未受影响任务可以继续汇报。
- 暂停期间和旧版本执行结果仍不能提交为当前版本成果。
- 取消审核恢复原任务状态；失败保留回答与草稿，迟到 AI 结果不能覆盖新版本。
- 联合发布保持原子性；改需求后旧分工不能继续发布。
- 完成必须携带真实版本和非空验收证据，重复汇报保持幂等。
- 已完成任务受影响时创建关联后续任务，保留原完成与验证事实。

## 检查与交付

在仓库的 `vibe-git/` 子目录执行。阶段 1 后运行协议构建和 Host 定向检查；交付前运行现有后端测试与完整构建：

```powershell
npm.cmd run build -w @vibe-git/protocol
npm.cmd run test -w @vibe-git/host

# 最终交付检查
npm.cmd test
npm.cmd run build
```

上述 `vibe-git/` 工作区子目录的 `npm.cmd run build` 已包含 Protocol、Host、CLI、Relay 和前端生产构建，前端输出仍为 `apps/web/dist-agile`。前端只做编译与 build，不安排浏览器、截图或前端端到端验证；交互由用户自行验证。必要的非平凡业务检查留在现有后端测试中，不为文案、改名或复制按钮编写镜像测试。

按上述阶段交付，每个阶段形成可运行的增量。交付说明记录已完成项、实际检查结果、用户可进入的操作路径，以及剩余限制。

本轮范围之外：自动打断任意已经运行的开发 AI、常驻协作 Agent、新安装器、技术栈迁移、完整 Git 托管平台功能。暂停同步的实际边界会明确告知用户。
